# Contributor guidance

Keep README friendly and concise: purpose, audience, skill overview, easy install/first use, and links. Change it for newcomer-relevant installation, starting, or major-capability changes; no README edit is required for every issue. Compatibility belongs in `docs/compatibility.md`; installation/troubleshooting in `docs/install.md`; runnable checks/rubric in `docs/checks.md`; release history in `docs/changelog.md`. Link to these homes rather than copying their tables. Dated check results stay in ignored local `docs/results/`, with their original revisions and dates; published documentation links only to tracked files.

Keep the README warm and lightly playful, with the learning inspiration and installation near the top. Include expandable Codex and Claude installation commands in the README, with the detailed-guide link at the end of the installation section. Introduce a small starter set before the specialized skills; keep the full toolkit later or expandable so newcomers have an easy first choice. Omit a general navigation section such as “Take a look around.”

Keep proposed README edits local until the user approves pushing them. Present the concrete README changes for review before requesting push approval. Other authorized changes follow the normal task workflow without a separate push-approval requirement.

Start with `node scripts/validate.mjs` and script syntax checks. Test changed runner behavior through its public conversation boundary with `node --test scripts/checks.test.mjs`. For skills, test the learner-visible conversation boundary; use the existing scenarios/rubric before adding a framework. Before model-backed execution, state affected skills/behavior/host and anticipated conversations/turns/retries. No routine approval gate. Stop after relevant passes; broaden only for failures, unresolved shared changes, or releases, with the reason stated. Avoid a subject-by-skill-by-host matrix. The runner supports Codex and Claude Code CLI hosts; one passing host is enough for a scoped teaching-behaviour change, and the other host is run only when a failure, host-specific metadata, or a support claim calls for it. The initial representative subjects are mathematics and history.

Automated checks and agent review are separate. Mark unreviewed quality unverified. Distinguish blocked prerequisites, observed failures, and missing evidence. CLI/image-inspection results do not verify desktop display; the user personally verifies rendering. Verify each desktop host independently, including native permission-before-activation and installed updates. Withhold verified support when requirements fail or cannot be checked; never weaken explicit permission to make packaging pass.

Skills follow Anthropic's [skill-authoring best practices](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices). `node scripts/validate.mjs` enforces these rules: a third-person description that says what the skill does and when to use it, no XML tags or reserved words, a SKILL.md body under 500 lines, forward-slash paths, and reference files at most one level deep. Use one term per idea in a skill, and match the terms in `CONTEXT.md`. Keep each skill's instructions in its SKILL.md and don't split them into reference files: the Claude check host runs with every tool disabled, so it can't read a linked file, and the bodies are well under the size limit. Keep the `lk-*` names; renaming them would break installed selections. Leave copyable progress checklists out of learner-facing replies.

Keep one set of teaching instructions in `skills/`, preserving all four as independently usable packages. Host manifests/catalogs can differ; do not copy the teaching bodies. Keep both plugin manifest versions and catalog metadata consistent. Every release changes the version and adds concise release information. The first plugin candidate has no previously verified installed-plugin update; record that gap instead of inventing a predecessor.

Synthetic transcripts, reports, and cached source images are local under ignored `.local/checks/`; concise dated reviews stay in ignored `docs/results/`. Older `docs/smoke-checks.md` and `docs/release-acceptance.md` are also ignored local references. Keep all result records for local reference and exclude them from commits and pushes. Published compatibility/release guidance still states known limitations without copying run logs or result tables. Actual learner conversations are excluded. Keep reusable fixtures, scenarios and review criteria tracked. Source image usage conditions remain separate from the project's software license.
